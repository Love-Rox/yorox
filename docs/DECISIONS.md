# Yorox 設計決定記録

分散型で運用できるConnpass代替「Yorox」(寄合 + Rox)の初期設計決定。
2026-08-07 の設計セッションでの決定事項をまとめたもの。

## プロダクト概要

- 分散型イベント管理プラットフォーム。Connpassの代替
- ActivityPub による連合を将来対応(MVPは単体動作)
- Rox とは独立したプロダクト(連携できると嬉しいが統合は前提としない)
- リポジトリ: Love-Rox/yorox(モノレポ)

## アカウントモデル

- 統一アクターモデル: ローカルもリモートも同一テーブル
- 3状態: ローカル / リモート未claim / リモートclaim済み
  - リモートユーザーの初回インタラクション時にエイリアスアカウントを自動生成
  - claim = 「このFediverseアカウントは自分のもの」の証明とエイリアスへの紐付け
- claim認証: OAuth主体(Mastodon/Misskey等を個別対応)、フォールバックでワンタイムコード検証
- 同一人物の複数アクターは統合可能(履歴マージを実装)
  - `alsoKnownAs` / `Move` の語彙に乗せ、吸収された側はリダイレクト化
- 外部公開するAPアクターは当初イベント/グループのみ
  - 全ユーザーにアクターURIは最初から割り当てておき、露出だけ止める(将来のユーザーアクター公開に備えてID体系を壊さない)

## 参加フロー / 枠ポリシー

枠(参加枠)は以下5要素のポリシーを持ち、すべてイベント(枠)単位で主催が選択する:

1. **方式**: 先着 / 抽選
2. **補欠モデル**: Connpass流(落選=補欠) / Reject分離(主催が補欠数を設定)
3. **繰上ポリシー**: 即時自動 / 締切付き自動(開催X時間前で停止) / 本人承諾型
   - 承諾型はローカル/claim済みユーザー向け機能と割り切る(未claimリモートには承諾UIを出せない)
4. **抽選ロジック**: 完全ランダム / 主催の手動選定 / 出欠率による重み付け
5. **参加条件**: claim済みのみ / アカウント年齢 / 参加実績 などの宣言的ルールのAND組合せ
   - `Join` 受信時に評価、満たさなければ理由付き `Reject`(summary に人間可読の説明)

### AP写像

- 抽選枠への `Join` → `TentativeAccept`(抽選待ちを明示)→ 当選で `Accept`
- 補欠は `TentativeAccept` 状態を維持し、繰上時に `Accept`
- 先着枠は `Join` に即 `Accept`(参加条件ゲートで防衛)

### 出欠 / no-show

- no-show を記録し、主催に出欠率を表示(抽選の判断材料)
- 実装上の配慮: 本人にも同じ数値を見せる / 母数を併記(コールドスタート保護) / リモートエイリアスは自インスタンス分のみ(評判の連合はしない)

## グループ

- イベントの所有者は常にグループ。個人主催も内部的には個人グループ(GitHubのユーザー名前空間方式)
- 個人グループのフォロー ≒ ユーザーのフォローに近くなる点は認識済み。将来ユーザーアクター公開時に個人グループと統合するか併存させるかは保留
- 権限はカスタムロール: 権限フラグ(イベント作成/編集/出欠管理/抽選実行/メンバー管理/グループ設定…)の束としてロールを定義
  - プリセット(オーナー/共同主催/メンバー)を同梱
  - 制約: 全権限を持つメンバーが最低1人

## 通知

- プラガブルドライバ設計: ドメインイベント → ディスパッチャ → ドライバ群(メール / Web Push / Webhook を同列に)
- 承諾型繰上のような「本人が確認しないと進まない」通知は、通知ドライバとは別に「アクション要求」を一段上の概念として持つ(配達保証・既読が必要)

## ディスカバリ

- リレー/クローラプロトコルを公開仕様化し、誰でもアグリゲータを建てられるようにする
  - Push経路: リレー購読で公開イベントの `Create` / `Update` / `Delete` を配信
  - Pull経路: `/.well-known` + NodeInfo で宣言、公開イベントのページネーション可能フィード
  - `Tombstone` を受けたアグリゲータは掲載を消す義務を仕様に明記
- 集約のデフォルトはインスタンス管理者が決め、主催がイベント単位で上書き

## モデレーション

- 連合ポリシーは denylist 型で出荷(開放デフォルト、Mastodon流)
- 先着枠へのリモートJoinは枠ポリシーの「参加条件」でゲート
- 通報(`Flag`)はカテゴリでルーティング: イベント内の問題→主催、主催自体の問題→インスタンス管理者
  - エスカレーション経路(主催宛て通報の放置時に管理者へ引き上げ)を用意
  - リモートからの `Flag` はカテゴリが無いので一律管理者キューへ

## コンテンツ

- 発表/セッションは任意機能の一級エンティティ(使わなければConnpass流のイベント直下資料に見える)
- 資料の紐付け先は「イベント or セッション」のどちらか
- 資料は外部リンク中心。ファイルホスティングはインスタンス設定で有効化(容量上限付き、実体はR2等のプラガブルストレージ)
- AP上は資料を `Document` としてコレクションに `Add`(開催後の資料公開が連合に流通する)
- 参加者一覧: イベント単位で主催が設定、**デフォルトは公開**(Connpass流)
  - 本人が自分を一覧から隠すオプトアウトは初期リリース必須
  - 非公開設定時、APの参加者コレクションは公開デリファレンス不可(authorized fetch 要求)

## 技術スタック

- **Cloudflareファースト**: Workers / D1 / Queues(AP配信リトライ) / Durable Objects(先着枠の定員直列化) / Cron Triggers(抽選締切・繰上) / R2(資料ホスティング有効時)
- **AP層**: このプロダクト用にゼロ依存で新規実装(Roxからの切り出しはしない)
- **フロントエンド**: Waku(RSC)。内部がHonoベースなので `/inbox` や `/.well-known/webfinger` 等のAPエンドポイントをHonoルートとして同居
- **データ層**: D1 + Drizzle(型付きスキーマ + マイグレーション)
  - ゼロ依存はライブラリ(AP層)の規律。アプリ本体はDXを優先
- **リポジトリ**: モノレポ。`packages/app` / `packages/ap`(ゼロ依存APライブラリ) / 将来 `packages/aggregator`

## MVPスコープ

成功条件: **単体でConnpass代替として、自分のイベントを1つ開催しきれる**(ドッグフーディング)

含む:
- アカウント: ローカルのみ(アクターURIは予約)
- 枠: 先着+抽選+補欠のフルセット、枠ポリシー選択UIも含めフル実装
- グループ: 作成+カスタムロール含めフル実装
- コンテンツ: Markdown本文+資料リンク+セッション構造
- 通知: プラガブルIF+メールドライバ1本(Resend等の送信API経由)

後回し:
- AP連合一式(配信、claim/エイリアス、Mobilizon相互運用)
- アグリゲータプロトコル
- Web Push / Webhook ドライバ
- 資料ファイルホスティング

連合を意識するのはID/URL設計のみ。連合前提のURL設計をMVP時点で守ること。
